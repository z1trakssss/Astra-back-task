# Astra · аналитика продаж стройматериалов

Решение отборочного задания по backend разработке. Источник - [US Building Materials Sales Transactions 2019-2024](https://www.kaggle.com/datasets/sergionefedov/us-building-materials-sales-transactions-20192024), лицензия CC0. Данные синтетические: выводы на панели описывают закономерности этого набора, а не фактическую ситуацию на рынке США.

## Что реализовано

| Часть | Результат |
| --- | --- |
| 1.0 | Полный исходный архив в `data/source.zip`, потоковый импорт 340 тыс. транзакций в PostgreSQL, валидация исходных полей |
| 1.1 | Импорт 313 недель из `macro_drivers_weekly.csv`, связь недели с продажами |
| 2.1 | Django API: фильтры, страницы, агрегация, отдельный ряд показателей |
| 2.2 | Unfold: таблица, поиск, фильтры, панель с графиками, кнопка XLSX отчёта |
| 3.1 | Dockerfile и Compose для готового образа и сборки из исходников |
| 3.2 | Эта инструкция и докстринги основных компонентов |

## Архитектура данных

В архиве три файла:

- `building_materials_transactions.csv`: факт продаж. `date` - понедельник недели, поля `year`, `month`, `week_of_year` производны от даты, а три макропоказателя повторяются в каждой строке;
- `macro_drivers_weekly.csv`: независимый ряд макропоказателей и `season_factor`, один набор значений на неделю;
- `data_dictionary_materials.csv`: описание колонок, не бизнес таблица.

Контроль после полного импорта: 340 000 продаж, 313 недель с 7 января 2019 по 30 декабря 2024 года, 47 939 567 единиц товара и 590 657 665,05 USD выручки. Наибольшая выручка у региона `South_Atlantic` (123 461 934,27 USD) и категории `lumber` (218 761 038,44 USD). Эти числа помогают быстро обнаружить неполный импорт.

Выбрана PostgreSQL: транзакционная целостность, внешние ключи, индексы и агрегаты SQL подходят для совместной работы API и админки с 340 тыс. строк. Отдельная аналитическая СУБД здесь добавила бы сложность эксплуатации без ожидаемой пользы. Для локальных тестов настройки допускают SQLite.

В БД две основные таблицы. `MacroWeek.week` - ключ недели; `Sale.week` - внешний ключ. Из продажи не копируются `year`, `month`, `week_of_year` и показатели: дата даёт календарные поля, а показатели берутся по связи. Преимущества - единый источник значения и компактное хранение, возможность добавить новые показатели без изменения фактов. Недостатки - JOIN при выдаче показателей и необходимость сначала загрузить недельный ряд. Команда импорта проверяет, что повторённые значения показателей и календарные поля совпадают с недельным файлом. `source_row` сохраняет позицию исходной строки и делает повторный импорт безопасным. Фильтрация и агрегация выполняются в БД.

Текстовые значения региона, категории и канала хранятся в факте с индексами. Их небольшой набор и стабильность делают отдельные таблицы справочников избыточными; таких таблиц в исходном архиве нет.

## Запуск

Требуются Docker и Docker Compose. Из корня проекта:

```bash
docker compose -f compose.yml -f compose.build.yml up --build
```

Compose собирает образ, поднимает PostgreSQL, применяет миграции, загружает полный архив и запускает веб приложение. Статика админки отдаётся WhiteNoise. Первый импорт занимает некоторое время. База хранится в томе `postgres_data`; последующие запуски не дублируют транзакции.

Для режима готового образа заранее соберите его с тегом `astra-backend:local`:

```bash
docker build -t astra-backend:local .
docker compose -f compose.yml up
```

В демо конфигурации админка доступна на `http://localhost:8000/admin/`, пользователь `demo`, пароль `demo-only-change-me`. Эти значения предназначены только для локального запуска. Перед размещением на сервере задайте свои `DJANGO_SECRET_KEY`, пароль БД и учётную запись администратора, настройте HTTPS и `DJANGO_ALLOWED_HOSTS`.

## API

| URL | Назначение |
| --- | --- |
| `/api/v1/sales/` | Продажи, до 200 строк на страницу; `page`, `page_size` |
| `/api/v1/sales/aggregate/` | Сводка по `month`, `week`, `region`, `product_category`, `sku`, `channel` или `customer_type` |
| `/api/v1/macro/` | Недельный ряд показателей |
| `/health/` | Проверка соединения с БД |

Оба маршрута продаж принимают точные фильтры `region`, `product_category`, `sku`, `channel`, `customer_type` и даты `date_from`, `date_to` включительно в формате `YYYY-MM-DD`. Денежные суммы и индексы возвращаются строками, чтобы клиент не терял точность десятичного типа.

Примеры:

```text
GET /api/v1/sales/?region=Pacific&date_from=2021-01-01&page_size=20
GET /api/v1/sales/aggregate/?group_by=product_category&channel=pro_dealer
GET /api/v1/macro/?date_from=2021-01-01&date_to=2021-12-31
```

На главной странице админки показаны последние 12 месяцев, регионы и категории по выручке. Кнопка XLSX над списком продаж создаёт сводку по категориям с учётом фильтров региона, категории, канала, типа клиента, диапазона дат и поиска. Для больших отчётов выгружается агрегат, а не сотни тысяч исходных строк.

## Разработка и проверки

Для локального Python 3.12+ без Docker:

```bash
python -m venv .venv
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_dataset
python manage.py test
python manage.py runserver
```

При отсутствии `POSTGRES_HOST` используется SQLite. Исходный архив включён в репозиторий, поэтому ключ Kaggle не нужен. `python manage.py import_dataset --limit 1000` полезен для короткой проверки. Команда безопасна при повторном запуске. Миграции лежат в `sales/migrations/`.

GitHub Actions запускает тесты Django и отдельно проверяет сборку Compose, импорт полного архива в PostgreSQL и ответ API.

Структура: `config/` - настройки и маршруты; `sales/models.py` - модель данных; `sales/management/commands/import_dataset.py` - ETL; `sales/api.py` и `sales/filters.py` - API и общий фильтр; `sales/admin.py`, `sales/dashboard.py`, `templates/` - интерфейс администратора; `sales/tests.py` - проверки поведения.
